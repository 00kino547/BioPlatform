- [x] **Unset `PORT` silently binds the backend to port 0 instead of the intended 3000 (done 2026-10-06).** Found while disposable-testing `:canary`: the container started, logged `Database connected` and `Server running on port 0`, reported no error, and simply never answered its healthcheck. Root cause is a mismatch, not a missing default — `apps/backend/src/config/env.ts:29` has `PORT: z.coerce.number().default(3000)`, but `docker-compose.yml:74` passes `PORT: ${PORT}` with no `:-` fallback. An unset host variable therefore arrives as the **empty string**, not `undefined`, so `.default()` never fires and `z.coerce.number()` evaluates `Number("")` = `0`. `.default()` only fires on `undefined`, so the schema's own fallback is unreachable through compose. `PORT` is the **only** numeric var in `docker-compose.yml` passed bare — every other one (`TRUST_PROXY`, `SMTP_PORT`, `MEDIA_CACHE_MAX_*`, `AUTH_LOG_RETENTION_DAYS`, `UPDATE_CHECK_*`, `ACME_*`, `PASSKEY_*`, `ORPHAN_CLEANUP_*`) correctly uses `${VAR:-default}`, which makes this a single-site fix. Fix both ends: make it `PORT: ${PORT:-3000}` to match the file's own convention, **and** make the schema treat an empty string as absent (preprocess `""` → `undefined` before coercion) so the default is reachable again regardless of how the variable is supplied, including a bare `docker run -e PORT=`. Second half matters because the failure is silent — the process reports success while being unreachable, which is exactly what an automated installer must never be able to mistake for a healthy boot. **Done:** both ends fixed in `apps/backend/src/config/env.ts` (`emptyToUndefined` + `z.preprocess` before coercion) and in **both** compose files (`PORT: ${PORT:-3000}`); `tests/port-resolution.test.ts` — **10/10** for unset/empty/`3001` across both files, and the entrypoint probe confirmed `Server running on port 3000` with an empty `PORT`.
